# 📑 Профессиональная шпаргалка по коммитам в Git

Эта шпаргалка основана на стандарте **Conventional Commits** (семантические коммиты). Использование этого подхода делает историю проекта читаемой, предсказуемой и позволяет быстро ориентироваться в изменениях.

---

## 🏗️ Структура идеального коммита

<тип>(<контекст>): <краткое описание в повелительном наклонении>

[необязательное детальное описание (тело коммита)]

[необязательный футер (ссылки на задачи, breaking changes)]

*Пример:* `feat(auth): добавить проверку пароля при входе`

---

## 📊 Полный список ситуаций и типов коммитов

| Тип | Когда использовать (Ситуация) | Пример сообщения |
| :--- | :--- | :--- |
| **`feat`** | Добавление новой функциональности, формы, компонента или логики. | `feat(api): создать базовую структуру для обработки PHP-запросов` |
| **`fix`** | Исправление ошибки, багов, падений приложения. | `fix(forms): устранить NullReferenceException при закрытии окна` |
| **`wip`** | Работа в процессе. Срочное сохранение незаконченного кода. | `wip: перенос на ноут, логика базы данных не дописана` |
| **`refactor`**| Улучшение структуры кода без изменения его логики и без багфиксов. | `refactor(db): перевести запросы к Entity Framework на асинхронные` |
| **`style`** | Правки форматирования (пробелы, отступы, скобки, удаление лишних using). | `style(ui): выровнять элементы на главной форме` |
| **`docs`** | Изменения только в документации или комментариях к коду. | `docs: добавить описание методов подключения к MySQL` |
| **`perf`** | Оптимизация, которая напрямую улучшает производительность. | `perf(sql): ускорить выборку пользователей через добавление индекса` |
| **`test`** | Добавление или исправление тестов. | `test(auth): написать тесты для проверки валидации email` |
| **`build`** | Изменения в зависимостях, пакетах NuGet или файлах конфигурации. | `build(nuget): обновить пакеты для .NET Framework 4.8` |
| **`ci`** | Изменения в скриптах автоматизации или GitHub Actions. | `ci: добавить скрипт для автоматической сборки релизов` |
| **`chore`** | Рутинные задачи (обновление .gitignore, удаление временного мусора). | `chore: добавить папку .vs в исключения .gitignore` |
| **`revert`**| Отмена предыдущего коммита, если код сломал приложение. | `revert: отменить коммит "feat: добавить темную тему"` |

## 💡 Золотые правила написания сообщений

1. **Используй повелительное наклонение (Imperative Mood)**
   * ❌ *Неправильно:* `исправил баг`, `добавлена кнопка`, `fixing error`
   * ✅ *Правильно:* `исправить баг`, `добавить кнопку`, `fix error`
   * *Лайфхак:* Сообщение должно грамматически продолжать фразу: *"Если применить этот коммит, то он... **[текст вашего коммита]**"*.

2. **Ограничение по длине (Правило 50/72)**
   * Первая строка (заголовок) должна быть емкой — **до 50-60 символов**.
   * Если нужно расписать детали, оставь **пустую строку** после заголовка и пиши детальное тело коммита.

3. **Никакой точки в конце заголовка**
   * Заголовок коммита — это краткое название действия. Точка в конце первой строки не ставится.
